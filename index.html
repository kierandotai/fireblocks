Agent Spend Guard

An AI agent pays merchants in USDC from a Fireblocks vault. Every payment has to clear four gates before anything signs. Pick a scenario and watch where it stops.

Source on GitHub
  1. 1Request integrity

    Merchant-signed x402 requirement. Signature, expiry, nonce.

  2. 2Delegation grant

    User-signed grant to the agent. Validity window, revocation.

  3. 3Mandate scope

    Per-payment cap, 24h cap, velocity, merchant and asset allowlists.

  4. 4Workspace policy

    Ordered first-match rules, Inspector-style trace, then createTransaction.

Attacks

Man-in-the-middle payTo reroute

A compromised proxy between agent and merchant swaps the payTo address for an attacker wallet. Amount, merchant name and resource look untouched.

Expected: Blocked at integrity: merchant signature no longer verifies.

Two authorities, both required

Gates 2 and 3 are what the user delegated to the agent. Gate 4 is what the organization allows anyone to do. The KYT and escalation scenarios show a payment the user authorized that the workspace still stops. The injection scenario shows the reverse: the workspace would catch it, but the mandate catches it first.

Integrity before authority

Policy evaluates the destination it is shown. If a proxy swaps payTo in transit, a correct policy approves the wrong address. Verifying the merchant's signature over the full requirement closes that gap before any rule runs. The nonce is reused as the Fireblocks idempotency key, so a replay is stopped twice.

What is real here

Ed25519 signing and verification, the gate logic and the rule engine run for real on every click. Merchants, wallets and the policy are fixtures. The final step builds a real createTransaction request with the official TypeScript SDK. This page runs entirely in your browser and shows that payload; npm run sandbox in the repo sends it to a real sandbox workspace.
